# boxd MyGo 桌面端快速原型 EARS 任务清单

日期：2026-11-11

状态：待评审

关联设计：`docs/boxd/specs/2026-08-02-wails3-desktop-design.md`

## 1. 目标

在保留现有 Wails 桌面应用和发布流程不变的前提下，新建独立的 `desktop-mygo/` 子模块，使用 `github.com/egoist/mygo` 原生 UI 快速实现可运行原型，验证以下问题：

1. MyGo 原生 UI 是否适合 boxd 的桌面交互和视觉风格。
2. 现有 `internal/core`、`internal/service`、`internal/model` 是否能直接复用。
3. 原生应用能否稳定承载实时状态、流量图表、列表和长时间运行。
4. Linux 下窗口、托盘、单实例、隐藏启动和 GTK3 运行环境是否可用。
5. 原型资源占用和响应性是否具备继续迁移的价值。

## 2. 范围

### 2.1 本轮包含

- 新增 `desktop-mygo/` 独立 Go 模块。
- 使用 MyGo 原生 UI，不使用 WebView、HTML、CSS 或 JavaScript。
- 复用现有 core/service/model 和内嵌运行模式。
- 实现应用 Shell、主题、侧边栏和原型页面路由。
- 实现 Dashboard、服务控制、流量图表、节点、订阅、连接、日志和设置页面。
- 实现托盘、隐藏到托盘、单实例、开机自启和隐藏启动的基础能力。
- 提供功能测试、构建验证、运行验证和短时稳定性验证。
- 保留与 `~/.boxd/` 的数据目录和配置格式兼容能力。

### 2.2 本轮不包含

- 不修改或删除现有 `desktop/` Wails 应用。
- 不替换默认发布产物，不修改现有 Wails 打包脚本。
- 不做完整页面 1:1 迁移。
- 不实现高级配置编辑器、原始 JSON 编辑、Diff、终端和完整远程模式。
- 不实现正式发布签名、自动更新和全平台安装包验收。
- 不要求新增代码达到 90% 行覆盖率；覆盖率不作为本轮原型门禁。
- 不将 MyGo 版本接入正式 CI 发布流程。

## 3. 设计基线

| 项目 | 决策 |
| --- | --- |
| 子目录 | `desktop-mygo/` |
| Go module | 独立模块，建议 `github.com/xuthus5/boxd/desktop-mygo` |
| 根模块引用 | 使用 `replace github.com/xuthus5/boxd => ..` |
| UI 模式 | MyGo 原生 UI，不使用 WebView |
| 版本策略 | 固定 MyGo `v0.9.0`，不使用 `@latest` 参与正式构建 |
| 数据模式 | 本轮只实现 embedded；remote 仅保留接口边界和提示 |
| 数据目录 | 默认沿用 `~/.boxd/`，支持现有环境变量覆盖 |
| 主平台 | Linux；Windows/macOS 先做编译检查，不做完整验收 |
| 视觉规范 | 以 shadcn 的 token 和组件语义为目标，使用原生组件实现 |
| 测试策略 | 核心逻辑单测 + `ui.Tester` 视图测试 + Linux smoke；不设覆盖率门禁 |

## 4. 角色与术语

- 用户：启动 boxd 桌面应用并管理内核、节点、订阅和连接的人。
- 系统：`desktop-mygo` 原型应用。
- 运行时：bbolt、SettingsManager、SBInstance、ServiceSet 及其依赖。
- 原型页面：本轮实际实现的有限页面集合。
- EARS：
  - 通用型：系统应……
  - 事件驱动型：当……时，系统应……
  - 状态驱动型：在……状态下，系统应……
  - 异常型：如果……，系统应……
  - 可选型：当启用……时，系统应……
  - 复合型：在……状态下，当……时，系统应……

## 5. 全局 EARS 约束

### NFR-001 隔离与兼容

系统应作为独立 `desktop-mygo/` 模块构建，并且不应修改现有 `desktop/` Wails 应用的源码、构建入口和发布产物。

### NFR-002 数据兼容

系统应在默认情况下继续使用 `~/.boxd/` 作为数据目录，并应保持现有数据库、配置文件和凭据格式不变。

### NFR-003 文件安全

当系统创建数据目录时，系统应以 `0700` 权限创建目录；当系统创建配置、数据库、日志等普通文件时，系统应以 `0600` 权限创建文件。

### NFR-004 错误处理

当系统调用返回错误时，系统应使用变量接收并处理；当错误确定可以忽略时，系统应使用 `_` 显式忽略；系统不应静默丢弃未声明的错误。

### NFR-005 线程安全

在后台刷新、窗口重绘和服务控制并发发生时，系统应保证共享状态读写安全，并且不应在 UI 主线程执行长耗时阻塞操作。

### NFR-006 生命周期

当应用退出时，系统应停止后台刷新、关闭日志订阅、停止 sing-box 内核并关闭数据库；系统不应遗留未取消的 goroutine 或未释放的订阅。

### NFR-007 原生依赖

系统应使用 MyGo 原生 UI 渲染界面，并且不应启动 WebView、WebKit 页面或前端开发服务器作为原型 UI。

### NFR-008 可维护性

系统应保持页面、状态、运行时和平台能力分层；单个函数不超过 50 行、单个代码文件不超过 300 行、嵌套不超过 3 层、位置参数不超过 3 个。

### NFR-009 代码质量

当原型代码完成时，系统应通过 `go build ./...`、`go test ./...`、`go vet ./...`、`golangci-lint` 和 `goimports-reviser`；本轮覆盖率不作为阻塞条件。

### NFR-010 临时产物清理

当测试或构建结束时，系统应清理临时数据库、测试配置、截图、日志和临时二进制；不应把测试产物提交到仓库。

### NFR-011 性能可观测

系统应记录启动耗时、空闲 CPU、RSS、页面切换耗时和 30 分钟 soak 结果，用于与 Wails 版本进行同场景比较。

### NFR-012 降级可用

如果某个非关键原生能力不可用，例如 Linux 托盘或通知服务，系统应显示可理解的错误或降级状态，并保持主窗口和内核控制可用。

## 6. 任务清单

### TS-001 创建隔离子模块

- 优先级：P0
- 依赖：无
- EARS：
  - 系统应提供 `desktop-mygo/` 独立 Go module，并使用根模块作为本地依赖。
  - 当开发者执行 `go build ./...` 时，系统应能独立构建，不影响根模块和 `desktop/`。
- 实施要点：
  - 新增 `go.mod`、`go.sum`、`main.go`、`mygo.json`。
  - 固定 `github.com/egoist/mygo v0.9.0` 和 `go 1.27.4`。
  - 添加 `replace github.com/xuthus5/boxd => ..`。
  - 添加 `.gitignore`，忽略 `build/`、临时数据库和本地运行产物。
- 验收标准：
  - `desktop-mygo` 可独立构建。
  - 根目录 Wails 构建文件未发生变更。
  - `git diff` 中不包含无关文件。

### TS-002 配置应用标识与资源

- 优先级：P0
- 依赖：TS-001
- EARS：
  - 系统应使用 `boxd` 作为应用显示名称，并使用独立于 Wails 版本的开发标识。
  - 当应用启动时，系统应展示 boxd 图标和版本号。
- 实施要点：
  - 配置 `mygo.json`：名称、identifier、版本、输出目录。
  - 从现有资源生成或复用合法图标，确保尺寸和格式符合 MyGo 要求。
  - 版本号从构建参数或默认 `dev` 注入。
- 验收标准：
  - `go tool mygo build` 能生成原型二进制。
  - 窗口标题、应用名称和图标正确。
  - 资源文件权限符合 NFR-003。

### TS-003 实现内嵌运行时引导

- 优先级：P0
- 依赖：TS-001
- EARS：
  - 当应用启动时，系统应解析 `BOXD_DATA_DIR`、`BOXD_CONFIG`、`BOXD_USERNAME` 和 `BOXD_PASSWORD`，并在未设置时使用兼容默认值。
  - 当应用启动时，系统应初始化数据目录、bbolt、设置、默认配置、凭据、SBInstance 和 ServiceSet。
  - 当运行时初始化失败时，系统应显示可读错误并阻止进入主界面，不应以空依赖继续运行。
  - 当应用退出时，系统应停止内核并关闭数据库。
- 实施要点：
  - 在 `desktop-mygo/internal/runtime/` 中实现最小引导。
  - 不直接导入 `desktop/` 的 `package main`。
  - 保留对 remote 模式的显式拒绝或未实现提示。
  - 所有目录和普通文件权限分别使用 `0700` 和 `0600`。
- 验收标准：
  - 使用临时数据目录能初始化成功。
  - 重复启动不会破坏已有数据库。
  - 初始化失败路径有测试或可复现验证。
  - 退出后无残留内核和数据库句柄。

### TS-004 建立应用状态与刷新循环

- 优先级：P0
- 依赖：TS-003
- EARS：
  - 在应用运行状态下，系统应周期刷新服务状态、流量和连接摘要。
  - 当刷新成功时，系统应更新界面状态并触发窗口重绘。
  - 如果刷新失败，系统应保留最后一次有效数据，并显示“数据可能已过期”的提示。
  - 当应用退出或窗口销毁时，系统应取消刷新 context，并且不应继续访问运行时。
- 实施要点：
  - 建立线程安全的 `AppState`，集中保存状态、错误、页面选择和刷新时间。
  - 使用独立 goroutine 和 ticker；UI 更新通过 MyGo 主线程机制完成。
  - 流量样本限制在固定长度，避免无限增长。
- 验收标准：
  - 状态刷新不会阻塞窗口。
  - 连续刷新 30 分钟无明显卡顿。
  - 退出后 goroutine 和订阅被取消。

### TS-005 实现 shadcn 风格原生设计基线

- 优先级：P0
- 依赖：TS-001
- EARS：
  - 系统应提供统一的背景色、卡片色、边框色、主色、危险色、弱化文字色、圆角和间距 token。
  - 当页面构建时，系统应使用统一组件，而不应在每个页面重复硬编码颜色和间距。
  - 系统应为浅色和深色主题提供一致的可读性。
- 实施要点：
  - 在 `internal/ui` 中实现主题 token、Card、SectionHeader、Toolbar、StatusBadge、EmptyState、ErrorBanner 等原生组件。
  - 视觉目标对齐现有 shadcn 风格，不追求与 React 组件结构一致。
  - 避免魔法数字，集中定义间距和圆角常量。
- 验收标准：
  - 页面无明显颜色或间距漂移。
  - 浅色/深色切换后文字和背景可读。
  - 组件可在 `ui.Tester` 中渲染和交互。

### TS-006 实现应用 Shell、导航和路由

- 优先级：P0
- 依赖：TS-005
- EARS：
  - 系统应提供固定侧边栏和主内容区域。
  - 当用户选择侧边栏项目时，系统应切换到对应原型页面，并且不应重启应用或重建运行时。
  - 当当前路由无效时，系统应回到 Dashboard。
- 实施要点：
  - 使用 MyGo Router 或等价页面状态管理。
  - 原型路由至少包括 `/dashboard`、`/nodes`、`/subscriptions`、`/connections`、`/logs`、`/settings`。
  - 侧边栏展示 Dashboard、资源、可观测性和设置分组。
- 验收标准：
  - 所有原型路由可进入。
  - 页面切换不会重复初始化运行时。
  - 无效路由有稳定回退。

### TS-007 实现加载、空状态、错误和过期状态

- 优先级：P0
- 依赖：TS-004、TS-005
- EARS：
  - 当页面首次加载且尚无数据时，系统应显示加载状态。
  - 当列表为空时，系统应显示明确的空状态说明。
  - 当操作失败时，系统应显示错误信息，并提供重试或关闭入口。
  - 如果后台刷新失败但已有旧数据，系统应在保留旧数据的同时标记数据已过期。
- 实施要点：
  - 统一错误模型，区分不可用、未运行、请求失败和未实现。
  - 错误信息不暴露凭据、密钥或完整内部堆栈。
- 验收标准：
  - 空、加载、错误、过期四类状态可分别复现。
  - 错误不会导致白屏或 panic。

### TS-008 实现窗口、托盘和单实例生命周期

- 优先级：P0
- 依赖：TS-003、TS-006
- EARS：
  - 当用户关闭主窗口时，系统应隐藏窗口到托盘，而不是直接退出。
  - 当用户从托盘选择“显示”时，系统应显示并聚焦主窗口。
  - 当用户从托盘选择“退出”时，系统应完成运行时清理后退出。
  - 当用户再次启动已运行实例时，系统应聚焦现有主窗口。
  - 如果托盘不可用，系统应记录错误并保持主窗口和退出路径可用。
- 实施要点：
  - 使用 MyGo 单实例锁、Tray 和窗口事件。
  - 退出路径只保留一个统一收尾入口。
  - 托盘菜单至少包含显示、隐藏和退出。
- 验收标准：
  - 关闭窗口后进程仍在托盘运行。
  - 再次启动不会产生第二个业务实例。
  - 托盘退出后进程、内核和数据库正常关闭。

### TS-009 实现应用偏好和开机自启

- 优先级：P1
- 依赖：TS-003、TS-008
- EARS：
  - 当用户启用开机自启时，系统应注册系统登录启动项。
  - 当应用由登录启动触发时，系统应默认隐藏主窗口并驻留托盘。
  - 当用户关闭开机自启时，系统应移除登录启动项。
  - 如果登录启动项注册失败，系统应恢复开关状态并显示错误。
- 实施要点：
  - 使用 MyGo `SetOpenAtLogin`、`OpenAtLogin` 和 `WasOpenedAtLogin`。
  - 不自行拼接 shell 命令。
- 验收标准：
  - 开关状态与实际系统状态一致。
  - 登录启动不会强制弹出主窗口。
  - 失败路径有错误反馈。

### TS-010 实现 Dashboard 状态卡和服务控制

- 优先级：P0
- 依赖：TS-004、TS-007
- EARS：
  - 当 Dashboard 打开时，系统应显示内核运行状态、运行时间、内存、版本和配置路径。
  - 当用户点击启动、停止或重启时，系统应调用现有 service 控制用例，并在操作期间禁用重复操作。
  - 当控制操作成功时，系统应刷新状态并显示成功反馈。
  - 如果控制操作失败，系统应显示错误，并保持界面状态与服务真实状态一致。
- 实施要点：
  - 调用 `ServiceSet.Service()` 的 `ServiceStatus`、`ServiceStart`、`ServiceStop`、`ServiceRestart`。
  - 长耗时操作放入 goroutine，避免阻塞主线程。
- 验收标准：
  - 三个控制动作均可完成。
  - 重复点击不会并发触发多次控制。
  - 操作失败后界面仍可继续使用。

### TS-011 实现流量图表

- 优先级：P0
- 依赖：TS-004、TS-005
- EARS：
  - 在应用运行状态下，系统应显示上传和下载速率的滚动趋势。
  - 当刷新产生新样本时，系统应追加样本并移除超窗口旧样本。
  - 如果流量数据不可用，系统应显示空状态而不是伪造数值。
- 实施要点：
  - 使用 `ServiceSet.Stats().Traffic` 和 MyGo `ui/chart`。
  - 固定窗口长度和刷新间隔，避免内存无限增长。
  - 同时展示当前上传量、下载量和总量。
- 验收标准：
  - 图表在 5 分钟刷新中持续更新。
  - 页面切换后无重复采样循环。
  - 无流量时显示 0 或空状态，不 panic。

### TS-012 实现节点页面

- 优先级：P0
- 依赖：TS-004、TS-005
- EARS：
  - 当节点页面打开时，系统应显示节点标签、类型、服务器、端口和最近测速状态。
  - 当节点数量超过可视区域时，系统应使用虚拟列表或等价机制，不应一次性构建全部行。
  - 当节点列表为空时，系统应显示导入提示。
- 实施要点：
  - 读取 `svc.Deps.NodeManager.List()` 和测速结果。
  - 原型只做只读展示，不在本轮实现节点新增、编辑和删除。
- 验收标准：
  - 空列表和非空列表均可正常显示。
  - 大量节点不会导致窗口首次打开明显卡顿。

### TS-013 实现订阅页面

- 优先级：P0
- 依赖：TS-004、TS-005
- EARS：
  - 当订阅页面打开时，系统应显示订阅名称、更新状态、流量和最近更新时间。
  - 当用户点击刷新时，系统应调用现有订阅刷新用例，并防止同一订阅重复刷新。
  - 如果刷新失败，系统应保留订阅列表并显示错误。
- 实施要点：
  - 使用 `ServiceSet.Subscriptions().List` 和 `Refresh`。
  - 原型只实现查看和手动刷新，不实现新增、编辑、删除和全部刷新。
- 验收标准：
  - 订阅列表可加载。
  - 单个订阅刷新可用。
  - 刷新失败不导致页面崩溃。

### TS-014 实现连接页面

- 优先级：P0
- 依赖：TS-004、TS-005
- EARS：
  - 当连接页面打开时，系统应显示活动连接数量、目标、出口、上传、下载、持续时间和规则摘要。
  - 当连接列表持续变化时，系统应保持列表可滚动，并且不应无限累积已关闭连接。
  - 当用户关闭单个连接时，系统应调用现有关闭连接用例并刷新列表。
- 实施要点：
  - 使用 `ServiceSet.Stats().Connections` 和 `CloseConnection`。
  - 本轮可不实现批量关闭和高级筛选。
- 验收标准：
  - 连接列表可显示和刷新。
  - 单个连接关闭成功或返回明确错误。
  - 长时间刷新后内存无持续增长趋势。

### TS-015 实现日志页面

- 优先级：P0
- 依赖：TS-003、TS-005
- EARS：
  - 当日志页面打开时，系统应显示最近的应用日志和内核日志。
  - 当新日志到达时，系统应以受控方式追加，并在用户停留底部时保持跟随末尾。
  - 当用户向上滚动时，系统不应强制跳回底部。
  - 当日志缓冲区达到上限时，系统应丢弃最旧日志并保留固定容量。
- 实施要点：
  - 使用 `core.LogWriter` 的 `Recent` 或订阅接口。
  - 页面关闭时取消订阅，避免循环中泄漏。
- 验收标准：
  - 日志可实时追加。
  - 用户滚动后不被强制拉回底部。
  - 页面反复打开关闭后无重复订阅。

### TS-016 实现设置页面

- 优先级：P1
- 依赖：TS-009
- EARS：
  - 当设置页面打开时，系统应显示主题、开机自启、内核自启、数据目录和版本信息。
  - 当用户修改可持久化设置时，系统应保存并显示结果。
  - 如果保存失败，系统应恢复界面状态并显示错误。
- 实施要点：
  - 复用 `ServiceSet.Settings()`。
  - 数据目录和版本先只读展示。
  - 本轮不实现密码、URL Test 和完整 UI 偏好。
- 验收标准：
  - 设置读取和保存路径可用。
  - 保存失败时不会出现界面值与持久化值不一致而无提示。

### TS-017 实现 Deep Link 基础入口

- 优先级：P1
- 依赖：TS-008
- EARS：
  - 当应用收到 `boxd://import?link=...` 时，系统应解析链接并聚焦主窗口。
  - 如果链接格式无效或导入未实现，系统应显示明确提示，不应崩溃。
- 实施要点：
  - 复用现有 `ParseBoxdURL` 语义，或在原型中实现等价解析。
  - 原型可只展示待导入链接，暂不执行完整导入流程。
- 验收标准：
  - 合法 URL 能触发应用内提示。
  - 非法 URL 和空参数被安全处理。

### TS-018 验证 Linux GTK3 原生窗口

- 优先级：P0
- 依赖：TS-006、TS-008
- EARS：
  - 当原型在 Linux 启动时，系统应使用 GTK3 原生窗口运行，并且不应依赖 WebKitGTK。
  - 在 HiDPI、深色主题和输入法环境下，系统应保持窗口可操作和文字可读。
- 实施要点：
  - 使用 `go tool mygo dev` 或有图形会话时运行构建产物。
  - 无图形会话时使用 `xvfb-run` 做启动 smoke。
  - 检查进程列表，确认没有 WebKit 进程。
- 验收标准：
  - Linux 窗口成功打开。
  - 关闭、最小化、托盘隐藏和恢复可用。
  - 原型运行不依赖 WebKitGTK。

### TS-019 编写原型功能测试

- 优先级：P0
- 依赖：TS-003 至 TS-016
- EARS：
  - 系统应为运行时配置、状态刷新、导航选择和错误映射提供单元测试。
  - 系统应使用 `ui.Tester` 验证 Dashboard、侧边栏导航、服务控制和空状态。
  - 当测试使用临时数据目录时，系统应自动清理临时文件。
- 实施要点：
  - 本轮不设覆盖率门槛，但关键成功路径和异常路径必须有测试或可复现 smoke。
  - 测试不得依赖真实网络、真实内核启动或用户主目录。
- 验收标准：
  - `go test ./...` 通过。
  - 测试结束后无临时数据库、配置和二进制残留。
  - 关键页面至少有可执行 smoke 覆盖。

### TS-020 构建、运行和静态检查

- 优先级：P0
- 依赖：TS-019
- EARS：
  - 当原型完成时，系统应通过构建、测试、`go vet`、`golangci-lint` 和 `goimports-reviser`。
  - 当构建 Linux 原型时，系统应生成独立二进制，不覆盖 `/usr/local/bin/boxd` 或现有 Wails 二进制。
- 实施要点：
  - 在 `desktop-mygo/` 内执行构建和检查。
  - 输出到 `desktop-mygo/build/` 或临时目录。
  - 清理测试产生的临时文件。
- 验收标准：
  - 所有检查命令有真实执行记录。
  - 构建产物路径明确，且不污染现有发布目录。

### TS-021 执行性能与 soak 基线

- 优先级：P1
- 依赖：TS-020、TS-018
- EARS：
  - 当原型持续运行 30 分钟时，系统应保持窗口可操作、流量刷新持续、内存无持续单调增长。
  - 当页面在 Dashboard、节点、连接和日志之间切换时，系统应保持非线性增长的内存占用。
  - 系统应记录启动耗时、空闲 CPU、RSS、页面切换耗时和最终结果。
- 实施要点：
  - 使用固定测试数据或现有配置。
  - 记录 Wails 和 MyGo 原型的同场景基线；本轮只输出报告，不设置强制性能门槛。
- 验收标准：
  - 产出可复现的性能记录。
  - 无窗口冻结、无 panic、无持续 RSS 增长。
  - 发现阻塞性问题时形成后续任务。

## 8. 原型完成标准

同时满足以下条件时，原型可进入评审：

1. `desktop-mygo/` 能独立构建和运行。
2. 原生窗口可打开，且无 WebView/WebKit 页面承载 UI。
3. Dashboard 可显示实时状态，并可启动、停止和重启内核。
4. 流量图表可持续刷新 5 分钟以上。
5. 节点、订阅、连接、日志和设置页面可访问。
6. 关闭窗口可隐藏到托盘；再次启动可聚焦已有实例；托盘可退出。
7. 30 分钟 soak 无崩溃、无窗口冻结、无持续内存增长趋势。
8. `go test ./...`、`go vet ./...`、lint 和格式化检查通过。
9. 现有 Wails 应用、构建脚本和发布流程未被修改。
10. 形成明确的继续迁移、局部混合或放弃 MyGo 的决策建议。

## 9. 风险与缓解

| 风险 | 影响 | 缓解方式 |
| --- | --- | --- |
| MyGo 仍为 0.x，API 可能变化 | 后续升级成本 | 固定 v0.9.0；集中封装主题和基础组件 |
| GTK3 与现有 Wails GTK4/WebKitGTK6 环境不同 | Linux 验证差异 | TS-018 单独验证 GTK3；打包时声明依赖 |
| 复杂表单和编辑器的原生实现成本高 | 原型超出时间盒 | 本轮只做只读列表和基础设置，不迁移高级编辑器 |
| 后台刷新与 UI 主线程竞争 | 卡顿或数据竞争 | TS-004 统一状态锁和取消模型；高耗时操作放 goroutine |
| 托盘在部分 Linux 桌面不可用 | 关闭窗口后无法恢复 | 托盘失败降级为主窗口常驻；记录兼容性结果 |
| 性能结论被单次体验误导 | 错误决策 | TS-021 固定场景记录启动、CPU、RSS 和 soak 数据 |

## 10. 决策门槛

原型评审时按以下方向决策：

- 继续迁移：核心页面可稳定运行，资源占用和响应性优于 Wails，且复杂页面具备可行替代路径。
- 局部混合：原生 Shell 和常用页面可行，但复杂配置编辑器仍需 WebView；需单独评审是否接受。
- 暂停 MyGo：关键交互、托盘、GTK3 或长时间稳定性存在阻塞性问题，继续维护 Wails。
