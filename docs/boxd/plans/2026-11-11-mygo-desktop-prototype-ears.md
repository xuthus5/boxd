# boxd MyGo 桌面端快速原型 EARS 任务清单

日期：2026-11-11

状态：原型已实现；基础能力无显示自动验收通过（提交 `0005728`，2026-11-12）；新增能力与真实桌面最终验收待完成

关联设计：`docs/boxd/specs/2026-08-02-wails3-desktop-design.md`

## 1. 目标

在保留现有 Wails 桌面应用和发布流程不变的前提下，新建独立的 `desktop-mygo/` 子模块，使用 `github.com/egoist/mygo` 原生 UI 快速实现可运行原型，验证以下问题：

1. MyGo 原生 UI 是否适合 boxd 的桌面交互和视觉风格。
2. 现有 `internal/core`、`internal/service`、`internal/model` 是否能直接复用。
3. 原生应用能否稳定承载实时状态、流量图表、列表和长时间运行。
4. Linux 下窗口、托盘、单实例、隐藏启动和 GTK3 运行环境是否可用。
5. 原型资源占用和响应性是否具备继续迁移的价值。

## 2. 范围

### 2.1 本轮包含

- 新增 `desktop-mygo/` 独立 Go 模块。
- 使用 MyGo 原生 UI，不使用 WebView、HTML、CSS 或 JavaScript。
- 复用现有 core/service/model 和内嵌运行模式。
- 实现应用 Shell、主题、侧边栏和原型页面路由。
- 实现 Dashboard、服务控制、流量图表、节点、订阅、连接、日志、Config 和设置页面。
- 实现托盘、隐藏到托盘、单实例、开机自启和隐藏启动的基础能力。
- 提供功能测试、构建验证、运行验证和短时稳定性验证。
- 保留与 `~/.boxd/` 的数据目录和配置格式兼容能力。

### 2.2 本轮不包含

- 不修改或删除现有 `desktop/` Wails 应用。
- 不替换默认发布产物，不修改现有 Wails 打包脚本。
- 不做完整页面 1:1 迁移。
- 不实现全部高级配置字段的原生可视化、配置 Diff、完整终端仿真和完整远程模式；Terminal 仅生成代理环境变量命令，不执行 shell；复杂配置仍使用原始 JSON 编辑器。
- 不实现正式发布签名、自动更新和全平台安装包验收。
- 不要求新增代码达到 90% 行覆盖率；覆盖率不作为本轮原型门禁。
- 不将 MyGo 版本接入正式 CI 发布流程。

- EARS：

## 5. 全局 EARS 约束

### NFR-001 隔离与兼容

系统应作为独立 `desktop-mygo/` 模块构建，并且不应修改现有 `desktop/` Wails 应用的源码、构建入口和发布产物。

### NFR-002 数据兼容

系统应在默认情况下继续使用 `~/.boxd/` 作为数据目录，并应保持现有数据库、配置文件和凭据格式不变。

### NFR-003 文件安全

当系统创建数据目录时，系统应以 `0700` 权限创建目录；当系统创建配置、数据库、日志等普通文件时，系统应以 `0600` 权限创建文件。

### NFR-004 错误处理

当系统调用返回错误时，系统应使用变量接收并处理；当错误确定可以忽略时，系统应使用 `_` 显式忽略；系统不应静默丢弃未声明的错误。

### NFR-005 线程安全

在后台刷新、窗口重绘和服务控制并发发生时，系统应保证共享状态读写安全，并且不应在 UI 主线程执行长耗时阻塞操作。

### NFR-006 生命周期

当应用退出时，系统应停止后台刷新、关闭日志订阅、停止 sing-box 内核并关闭数据库；系统不应遗留未取消的 goroutine 或未释放的订阅。

### NFR-007 原生依赖

系统应使用 MyGo 原生 UI 渲染界面，并且不应启动 WebView、WebKit 页面或前端开发服务器作为原型 UI。

### NFR-008 可维护性

系统应保持页面、状态、运行时和平台能力分层；单个函数不超过 50 行、单个代码文件不超过 300 行、嵌套不超过 3 层、位置参数不超过 3 个。

### NFR-009 代码质量

当原型代码完成时，系统应通过 `go build ./...`、`go test ./...`、`go vet ./...`、`golangci-lint` 和 `goimports-reviser`；本轮覆盖率不作为阻塞条件。

### NFR-010 临时产物清理

当测试或构建结束时，系统应清理临时数据库、测试配置、截图、日志和临时二进制；不应把测试产物提交到仓库。

### NFR-011 性能可观测

系统应记录启动耗时、空闲 CPU、RSS、页面切换耗时和 30 分钟 soak 结果，用于与 Wails 版本进行同场景比较。

### NFR-012 降级可用

如果某个非关键原生能力不可用，例如 Linux 托盘或通知服务，系统应显示可理解的错误或降级状态，并保持主窗口和内核控制可用。

## 6. 任务清单

### 6.1 任务验收统一要求

每个任务只有同时满足以下条件，才可标记为“完成”：

- 任务的 EARS 条款、实施要点和验收标准均已落实，没有用推断代替实际结果。
- 验收结果必须明确标记为“自动通过”“人工确认”“未验证”或“条件通过”，并引用可追溯的命令、日志、截图或测试名称。
- P0 任务必须通过对应的单元测试、集成测试、`ui.Tester` 视图测试或 Xvfb E2E；没有自动化证据时，必须记录可复现的人工步骤。
- 涉及持久化、错误路径或并发行为的任务，必须验证失败后旧数据保留、界面可继续操作，并执行 `go test -race ./...`；环境不支持时必须标记“未验证”。
- 无显示服务器上的自动验收只能证明 GTK3 窗口、布局、导航和基础稳定性；真实 GPU、Wayland、输入法、HiDPI、多显示器和托盘体验必须由 TS-026 人工确认。
- 每个任务的验收证据必须归档到 `desktop-mygo/artifacts/acceptance/<run-id>/`，不得提交临时数据库、二进制、Socket、凭据或用户隐私数据。
- 缺少验收证据或真实桌面结论时，不得把原型表述为 Wails 的正式替代品，只能给出“条件通过”或“继续验证”的结论。

| 任务范围 | 必须通过的自动证据 | 必须提供的人工或环境证据 | 直接判定失败的条件 |
| --- | --- | --- | --- |

| TS-003、TS-004、TS-008、TS-009、TS-015、TS-016 | 临时数据目录集成测试；成功与失败路径测试；并发相关任务执行 `go test -race ./...` | 托盘、登录启动和退出清理的人工步骤；不可用时记录环境限制 | 读写用户真实 `~/.boxd/`；退出后残留内核、数据库句柄、goroutine 或订阅 |

| TS-030、TS-031 | 监听地址与命令生成单元测试；可视化字段与 JSON 双向映射测试；非法输入和失败路径测试；Xvfb 路由巡检 | 截图审阅四类命令和配置表单；剪贴板等依赖桌面环境的能力单独记录 | 命令泄露完整订阅链接或凭据；表单覆盖未知字段；失败后丢失未保存内容 |
| TS-015、TS-032 | 复制/导出成功、取消和写入失败测试；临时目录与文件权限断言；内容一致性校验 | 在真实桌面执行一次原生保存对话框操作 | 取消后仍创建文件；导出权限不是 `0600`；错误被静默忽略 |

| TS-022 | README 构建和启动命令可复现；文档声明 Wails 仍为默认桌面端 | 新开发者按文档走通一次启动流程 | 文档把原型描述为已完成替代品，或命令无法按文档执行 |

### 6.3 任务验收记录格式

每个任务完成时，应在任务条目下补充以下验收记录；未写回记录的任务不得标记为“完成”：

- `状态`：只能为“自动通过”“人工确认”“条件通过”或“未验证”。
- `提交`：验收对应的 Git 提交 SHA；工作树有未提交改动时不得引用旧提交结论。
- `命令`：实际执行命令、退出码和执行时间，不得只写“已测试”。
- `证据`：截图、日志、测试名称或数据文件的具体路径。
- `环境限制`：说明无显示服务器、fake 后端、真实网络、真实内核、托盘或 GPU 等未覆盖范围。
- `残留风险`：已知缺陷、未验证项和后续任务编号；没有风险时明确写“无已知残留风险”。

如果代码、依赖、配置或验收脚本发生变化，必须重新执行受影响门禁并生成新的 `<run-id>`；不得复用旧提交或旧工作树的截图、soak 数据和“通过”结论。

### 6.4 无显示服务器的验收要求

当前研发服务器没有桌面显示环境时，最低验收组合为：

1. 在 `desktop-mygo/` 下执行 `go build ./...`、`go test ./...`、`go vet ./...`、`go tool mygo vet`、`go tool mygo build`、`golangci-lint run ./...`、`goimports-reviser ...`，并保存完整退出码。
2. 对涉及并发、持久化或错误恢复的改动执行 `go test -race ./...`；工具链不可用时记录原因并标记“未验证”。
3. 使用 `ui.Tester` 生成固定尺寸截图并断言关键文本、空状态、错误状态和主题；截图不得为空或复用旧轮次。
4. 使用 Xvfb、`-tags e2e` 构建和 `mygo-automation` 启动真实 GTK3 窗口，验证窗口类型、全部原型路由、关键交互、截图和退出清理。
5. 执行 30 分钟 soak，保存 `soak.csv`、环境信息和结束前截图；未执行时不得宣称长时间运行稳定。
6. 如需人工观察窗口，仅允许 x11vnc/noVNC 绑定 `127.0.0.1`，通过 SSH 隧道访问，并在结束后关闭会话。
7. 真实 GPU、Wayland、输入法、HiDPI、多显示器、托盘行为和主观流畅度由 TS-026 在用户真实桌面确认；服务器验收只能给出“无显示环境通过、真实桌面待确认”的条件结论。

### TS-001 创建隔离子模块

- 优先级：P0
- 依赖：无
- EARS：
  - 系统应提供 `desktop-mygo/` 独立 Go module，并使用根模块作为本地依赖。
  - 当开发者执行 `go build ./...` 时，系统应能独立构建，不影响根模块和 `desktop/`。
- 实施要点：
  - 新增 `go.mod`、`go.sum`、`main.go`、`mygo.json`。
  - 固定 `github.com/egoist/mygo v0.9.0` 和 `go 1.27.4`。
  - 添加 `replace github.com/xuthus5/boxd => ..`。
  - 添加 `.gitignore`，忽略 `build/`、临时数据库和本地运行产物。
- 验收标准：
  - `desktop-mygo` 可独立构建。
  - 根目录 Wails 构建文件未发生变更。
  - `git diff` 中不包含无关文件。

### TS-002 配置应用标识与资源

- 优先级：P0
- 依赖：TS-001
- EARS：
  - 系统应使用 `boxd` 作为应用显示名称，并使用独立于 Wails 版本的开发标识。
  - 当应用启动时，系统应展示 boxd 图标和版本号。
- 实施要点：
  - 配置 `mygo.json`：名称、identifier、版本、输出目录。
  - 从现有资源生成或复用合法图标，确保尺寸和格式符合 MyGo 要求。
  - 版本号从构建参数或默认 `dev` 注入。
- 验收标准：
  - `go tool mygo build` 能生成原型二进制。
  - 窗口标题、应用名称和图标正确。
  - 资源文件权限符合 NFR-003。

### TS-003 实现内嵌运行时引导

- 优先级：P0
- 依赖：TS-001
- EARS：
  - 当应用启动时，系统应解析 `BOXD_DATA_DIR`、`BOXD_CONFIG`、`BOXD_USERNAME` 和 `BOXD_PASSWORD`，并在未设置时使用兼容默认值。
  - 当应用启动时，系统应初始化数据目录、bbolt、设置、默认配置、凭据、SBInstance 和 ServiceSet。
  - 当运行时初始化失败时，系统应显示可读错误并阻止进入主界面，不应以空依赖继续运行。
  - 当应用退出时，系统应停止内核并关闭数据库。
- 实施要点：
  - 在 `desktop-mygo/internal/runtime/` 中实现最小引导。
  - 不直接导入 `desktop/` 的 `package main`。
  - 保留对 remote 模式的显式拒绝或未实现提示。
  - 所有目录和普通文件权限分别使用 `0700` 和 `0600`。
- 验收标准：
  - 使用临时数据目录能初始化成功。
  - 重复启动不会破坏已有数据库。
  - 初始化失败路径有测试或可复现验证。
  - 退出后无残留内核和数据库句柄。

### TS-004 建立应用状态与刷新循环

- 优先级：P0
- 依赖：TS-003
- EARS：
  - 在应用运行状态下，系统应周期刷新服务状态、流量和连接摘要。
  - 当刷新成功时，系统应更新界面状态并触发窗口重绘。
  - 如果刷新失败，系统应保留最后一次有效数据，并显示“数据可能已过期”的提示。
  - 当应用退出或窗口销毁时，系统应取消刷新 context，并且不应继续访问运行时。
- 实施要点：
  - 建立线程安全的 `AppState`，集中保存状态、错误、页面选择和刷新时间。
  - 使用独立 goroutine 和 ticker；UI 更新通过 MyGo 主线程机制完成。
  - 流量样本限制在固定长度，避免无限增长。
- 验收标准：
  - 状态刷新不会阻塞窗口。
  - 连续刷新 30 分钟无明显卡顿。
  - 退出后 goroutine 和订阅被取消。

### TS-005 实现 shadcn 风格原生设计基线

- 优先级：P0
- 依赖：TS-001
- EARS：
  - 系统应提供统一的背景色、卡片色、边框色、主色、危险色、弱化文字色、圆角和间距 token。
  - 当页面构建时，系统应使用统一组件，而不应在每个页面重复硬编码颜色和间距。
  - 系统应为浅色和深色主题提供一致的可读性。
- 实施要点：
  - 在 `internal/ui` 中实现主题 token、Card、SectionHeader、Toolbar、StatusBadge、EmptyState、ErrorBanner 等原生组件。
  - 视觉目标对齐现有 shadcn 风格，不追求与 React 组件结构一致。
  - 避免魔法数字，集中定义间距和圆角常量。
- 验收标准：
  - 页面无明显颜色或间距漂移。
  - 浅色/深色切换后文字和背景可读。
  - 组件可在 `ui.Tester` 中渲染和交互。

### TS-006 实现应用 Shell、导航和路由

- 优先级：P0
- 依赖：TS-005
- EARS：
  - 系统应提供固定侧边栏和主内容区域。
  - 当用户选择侧边栏项目时，系统应切换到对应原型页面，并且不应重启应用或重建运行时。
  - 当当前路由无效时，系统应回到 Dashboard。
- 实施要点：
  - 使用 MyGo Router 或等价页面状态管理。
  - 原型路由至少包括 `/dashboard`、`/nodes`、`/subscriptions`、`/connections`、`/logs`、`/config`、`/settings`。
  - 侧边栏展示 Dashboard、资源、可观测性和设置分组。
- 验收标准：
  - 所有原型路由可进入。

### TS-014 实现连接页面与连接管理

- 优先级：P0
- 依赖：TS-004、TS-005
- EARS：

  - 关闭筛选结果仅影响匹配连接；关闭全部仅影响当前快照内的连接。
  - 取消确认不会关闭任何连接；批量关闭失败不会导致页面崩溃。
  - 长时间刷新后内存无持续增长趋势。

  - 当验收节点和订阅管理时，脚本应导入并删除节点、创建并删除订阅，并确认连接筛选和批量关闭入口存在。
  - 如果 automation 连接失败、窗口不存在、关键元素缺失或截图失败，系统应以非零状态退出。
- 实施要点：
  - 新增 `scripts/mygo-headless-e2e.sh` 或等价脚本，统一管理 Xvfb、D-Bus、应用进程、automation Socket 和临时数据目录。
  - 每轮验收使用独立 `mygo-automation --session`，避免并行 E2E/soak 互相覆盖默认会话。
  - 如果 `dbus-run-session` 可用，则使用它提供基础会话服务；如果不可用，则复用已有 session bus，并记录托盘和会话相关能力未验证。
  - 窗口管理器和托盘面板作为可选增强，不阻塞基础窗口验收；如需要更完整的焦点、最小化验收，可另行安装 `openbox`。
  - 使用 MyGo `v0.9.0` 对应版本的 `mygo-automation`。
  - 每一步都使用 `--settle` 或 `idle` 等待界面稳定，不使用固定 sleep 代替事件等待。
- 验收标准：
  - 脚本能在无 `DISPLAY` 的服务器上完成启动、导航、截图和退出。
  - 生成的截图来自真实应用窗口，而不是 `ui.Tester` 的预览图。
  - 应用退出后 Xvfb、应用进程、Socket 和临时文件均被清理。
  - 脚本失败时保留必要日志和截图，便于定位问题。

### TS-025 提供按需远程可视验收

- 依赖：TS-024
- EARS：

  - 不默认安装或启动远程桌面服务，只在评审者明确请求时启用。
- 验收标准：
  - 评审者可通过 SSH 隧道看到并操作原型窗口。
  - 端口只绑定 `127.0.0.1`。
  - 会话结束后无遗留 VNC 和 Xvfb 进程。

### TS-026 执行真实桌面最终验收

- 优先级：P0
- 依赖：TS-021、TS-024、TS-025

  - 如果真实桌面验收未执行，验收结论应明确标记为“条件通过”，不应声称已经证明长时间运行无卡顿。

- 验收标准：
  - 用户完成并记录验收清单。
  - 无持续卡顿、窗口失焦、托盘无法恢复或日志刷新阻塞。
  - 若发现卡顿，保留发生时间、操作步骤和资源数据。

### TS-028 实现 Config 原始 JSON 编辑与文件导入导出

- 优先级：P0
- 依赖：TS-003、TS-007、TS-020

  - 格式化、校验、应用、导入和导出均有成功与失败路径证据。
  - 超限文件被拒绝；导出文件权限为 `0600`；失败后编辑内容不丢失。

### TS-030 实现原生 Terminal 与代理环境变量

- 优先级：P1
- 依赖：TS-003、TS-006、TS-019、TS-024
- EARS：

- 验收标准：

  - `ui.Tester` 断言四类命令标题与命令内容可见，错误状态和空状态可渲染。
  - Xvfb E2E 从侧边栏进入 Terminal，断言关键文本并生成非空截图。
  - 复制路径有测试证明只调用剪贴板接口，不执行 shell；无法自动验证真实桌面剪贴板时标记“未验证”。
  - 页面证据明确记录 fake 后端和环境限制，不将命令文本当作真实连通性证明。

### TS-031 实现 Raw Config 路由与原生可视化配置表单

- 优先级：P0
- 依赖：TS-028
- EARS：

- 实施要点：
  - 可视化表单以当前 JSON 对象为权威数据源；仅修改已知字段，保留未知字段和数组中的复杂对象。
  - 对数字、布尔、枚举和必填字段进行显式校验，错误使用变量接收并反馈到界面。

- 验收标准：

  - 至少一条自动化用例证明表单修改后原始 JSON 同步变化且出现未保存标记；至少一条失败路径证明内容不丢失。

### TS-032 实现日志复制、日志导出与配置历史导出

- 优先级：P1
- 依赖：TS-015、TS-028
- EARS：
  - 当用户复制日志时，系统应将当前日志内容写入剪贴板，并显示可读结果。
  - 当用户导出日志或配置历史时，系统应通过原生保存对话框写出普通文件，并在成功后显式校正为 `0600` 权限。

  - Xvfb E2E 至少验证 Logs 和 Config history 的 Copy/Export 入口可见；原生保存对话框无法自动操作时标记“未验证”。

## 7. 验收要求

本节是原型进入评审的最低验收基线。任何未执行、未记录或无法复现的项目都必须标记为“未验证”，不得用推断代替证据；只有通过本节验收并完成真实桌面确认后，才能形成“替代 Wails”的最终结论。

### AR-001 验收分层

系统应至少通过以下三层验收：

1. 视图层：`ui.Tester` 在无显示环境中运行，验证布局、状态、交互和截图。
2. 真实窗口层：Xvfb 中运行带 automation 插件的构建产物，验证 GTK3 窗口和应用级导航。
3. 真实桌面层：用户在本机桌面运行原型，验证 GPU 渲染、输入法、托盘和主观流畅度。

### AR-002 无显示环境范围

在服务器没有 `DISPLAY` 的环境中，验收应默认使用 `ui.Tester`，不应要求启动 WebView、WebKitGTK、浏览器或远程桌面服务。

### AR-003 截图证据

系统应保存以下验收截图：

- Dashboard 浅色主题
- Dashboard 深色主题
- 节点页面
- 订阅页面
- 连接页面
- 日志页面
- Config 页面
- 设置页面
- 至少一张真实 Xvfb 窗口截图
- 至少一张 30 分钟 soak 结束前截图

### AR-004 交互验收

当在 Xvfb 中执行真实窗口验收时，系统应完成以下交互：

- 启动应用并等待主窗口出现。
- 使用侧边栏依次打开所有原型页面。
- 触发一次服务状态刷新。
- 触发一次订阅刷新，或在不可用时确认错误提示。
- 触发一次连接列表刷新。
- 打开日志页面并确认日志区域存在。
- 打开 Config 页面，执行一次格式化或校验，并确认导入、导出入口存在。
- 切换主题并确认界面重绘。

### AR-005 长时间运行验收

当执行 30 分钟 soak 时，系统应每隔固定时间记录：

- 进程 RSS
- 进程 CPU
- 应用是否仍响应 automation 请求
- 页面是否仍可切换
- 流量图表是否仍在更新
- 是否出现 panic、崩溃或连接断开

### AR-006 失败判定

如果出现以下任一情况，验收应判定失败：

- 应用无法启动或主窗口不可见。
- automation 无法连接或关键元素缺失。
- 页面切换导致崩溃、空白窗口或长时间无响应。
- 截图与预期页面明显不符。
- 30 分钟 soak 中进程崩溃或持续无响应。
- 退出后遗留应用进程、Xvfb、automation Socket 或临时数据库。
- 验收过程修改或覆盖现有 Wails 应用和正式发布产物。

### AR-007 环境限制声明

如果只完成 Xvfb 和 `ui.Tester` 验收，结论应明确说明：

- 已验证 GTK3 窗口、布局、导航、自动交互和基础稳定性。
- 未验证真实 GPU 性能、Wayland、输入法、HiDPI 和多显示器。
- 长时间运行卡顿是否消失，仍需真实桌面最终验收后才能确认。

### AR-008 远程可视验收安全

当启用 noVNC 或 x11vnc 时，验收环境应仅绑定 `127.0.0.1`，通过 SSH 隧道访问，并使用临时密码和最小生命周期会话。

### AR-009 验收隔离与前置记录

- 当开始任一轮验收时，验收者应使用独立临时数据目录和独立应用实例，不应读写用户现有 `~/.boxd/` 数据，也不应覆盖现有 Wails 产物。
- 系统应记录提交 SHA、Go 版本、MyGo 版本、操作系统与内核、GTK3 版本、显示方式、屏幕尺寸、缩放比例、命令和起止时间。
- 如果无法完成数据目录隔离，验收应终止并标记为失败，不应在用户真实数据上继续执行。
- 如果某项环境信息无法获取，记录应明确标记为“未知”，不得省略后仍宣称环境一致。

### AR-010 自动化质量门禁

- 当原型进入验收时，系统应真实执行以下命令，并记录退出码：
  - `go build ./...`
  - `go test ./...`
  - `go vet ./...`
  - `go tool mygo vet`
  - `go tool mygo build`

  - `goimports-reviser -project-name github.com/xuthus5/boxd/desktop-mygo -company-prefixes github.com/xuthus5/boxd -imports-order std,general,company,project ./...`

### AR-012 截图与视觉验收

- 系统应在固定 `1440x900` 视口下生成 Dashboard 浅色、Dashboard 深色、节点、订阅、连接、日志、Config 和设置截图。
- 系统应从 Xvfb 中的真实应用窗口额外生成至少一张截图，并通过 automation 断言窗口类型为 `content`。
- 截图应满足：PNG 可正常解码、尺寸符合预期、关键文本存在、画面不是纯色空白、页面主体区域具有可辨识的明暗差异。
- 如果字体缺失、控件布局重叠、文字不可读或截图与目标页面明显不符，验收应失败或标记为“未验证”，不得只凭文件存在判定通过。
- 截图文件权限应为 `0600`，所在临时目录权限应为 `0700`；测试结束后只保留归档证据，不保留临时数据库和二进制。

### AR-013 状态、错误与异常路径

- 当页面首次加载且尚无数据时，系统应显示加载状态；当列表为空时，系统应显示空状态；当操作失败时，系统应显示错误提示。
- 如果后台刷新失败但已有旧数据，系统应保留最后一次有效数据，并明确显示“数据可能已过期”。
- 如果运行时初始化失败，系统应显示启动失败页并阻止进入空依赖主界面。
- 如果服务控制、订阅刷新或连接关闭失败，系统应保留可继续操作的界面，不应 panic、白屏或永久进入加载状态。
- 如果收到非法深链、缺失参数或窗口尚未创建时的深链，系统应安全忽略或显示错误，不应访问空窗口对象。
- 上述异常至少应通过 fake backend、单元测试或可复现 smoke 之一验证，并在证据中记录触发方式和结果。

### AR-014 生命周期与资源清理

- 当关闭主窗口时，系统应隐藏到托盘而非退出；当从托盘选择显示时，窗口应恢复并获得焦点。
- 当已有实例运行时，再次启动应聚焦现有窗口，不应创建第二个业务实例或第二套运行时。
- 当从托盘退出时，系统应停止后台刷新、关闭日志订阅、停止内核、关闭数据库，并在合理时间内退出进程。
- 如果托盘不可用，系统应保持主窗口和内核控制可用，并记录降级原因。
- 验收结束时，应用进程、Xvfb、automation Socket、临时数据库和临时二进制均应清理；清理失败应明确记录并判定验收失败。
- 验收脚本只能终止本轮自己启动的进程，不得终止用户或其他任务启动的进程。

### AR-015 性能与 30 分钟 soak 门槛

- 系统应在固定场景下持续运行至少 30 分钟，每 60 秒记录一次时间戳、RSS、CPU、automation 响应状态、当前页面、页面切换耗时和流量图表更新时间。
- 自动化 soak 通过的最低条件是：进程不崩溃、窗口不永久无响应、automation 仍可连接、七个页面仍可切换、流量图表仍持续更新、退出后无遗留资源。
- 如果 automation 请求 p95 超过 2 秒、页面切换超过 2 秒、连续两次采样窗口无响应，或后 15 分钟出现无法解释的持续 RSS 增长，应标记性能风险，不得直接得出“卡顿问题已解决”的结论。
- 若 30 分钟 RSS 相对第 5 分钟基线增长超过 64 MiB，应在验收报告中单独列出，并至少复测一次；复测仍出现时不得判定性能验收通过。
- Xvfb 使用软件渲染，只能证明基础稳定性和响应性；真实 GPU、Wayland、输入法、HiDPI、多显示器、托盘体验和主观流畅度必须在真实桌面使用同一场景复测。
- 只有真实桌面 30 分钟观察无明显持续卡顿、窗口失焦或托盘异常，并与 Wails 原型形成同场景对比记录后，才能通过最终性能验收。

### AR-016 边界与失败注入

- 系统应覆盖空节点、240 个节点、400 条日志、120 个流量样本、刷新失败、运行时初始化失败、服务控制失败和非法深链等边界场景。
- 系统应验证节点虚拟列表不会一次构建全部行，日志和流量缓冲区不会无限增长，已关闭连接不会无限累积。
- 如果任何边界场景导致 panic、窗口冻结、内存持续增长或无法恢复的错误页，验收应判定为失败。

### AR-017 Wails 隔离与兼容回归

- 验收前后，现有 `desktop/` Wails 应用源码、构建入口、发布脚本和默认产物不应发生变化。
- 系统应验证 MyGo 原型不启动 WebView、WebKit 页面或前端开发服务器；检查结果应记录在验收报告中。
- 如果根模块构建或现有 Wails 构建可执行，应至少执行一次并确认未被原型改动破坏；无法执行时标记为未验证。
- 如果 `git diff` 出现与当前原型无关的共享代码、根配置或依赖变更，应停止验收并拆分为独立任务。

### AR-018 安全、隐私与凭据保护

- 验收截图、日志、CSV 和总结中不应出现数据库内容、订阅链接中的敏感参数、JWT、密码、密钥或用户隐私数据。
- 所有临时目录使用 `0700`，普通文件使用 `0600`；确需可执行权限的脚本或二进制才可使用 `0700`。
- 远程可视验收只允许绑定 `127.0.0.1`，通过 SSH 隧道访问，并限制会话生命周期；验收结束后应停止 VNC、Xvfb 和应用进程。
- 如果无法确认证据不含敏感信息，该证据不得归档或提交。

### AR-019 验收结论与签署

- 每项验收要求应记录为“自动通过”“人工确认”“未验证”或“条件通过”之一，并引用对应截图、日志或数据文件。
- 所有 P0 级自动化门禁和页面验收通过后，原型最多只能获得“条件通过”或“继续投入原型”的结论；真实桌面未验收时不得宣称已经替代 Wails。
- 如果存在阻塞性失败项，结论应为“暂停 MyGo”或“局部混合”，并明确列出阻塞原因和后续验证任务。
- 最终结论应由用户或指定评审者确认，并记录确认日期和仍未验证的范围。

### AR-020 证据包规范

每次验收应在 `desktop-mygo/artifacts/acceptance/<run-id>/` 下保存以下证据，并确保该目录被 `.gitignore` 排除：

- `screenshots/`：约定的浅色、深色和各页面截图，以及真实 Xvfb 窗口截图。
- `logs/`：automation 日志、应用启动日志、导航日志和失败注入日志。
- `soak.csv`：30 分钟性能采样数据。
- `commands.txt`：实际执行命令、退出码和执行时间。
- `environment.txt`：提交 SHA、工具版本、显示方式和系统信息。
- `result.md`：逐项验收状态、证据路径、环境限制和最终结论。

如果任一结论无法追溯到具体证据，验收不得标记为通过。

### AR-021 无显示服务器推荐验收流程

在当前没有桌面显示环境的服务器上，验收应按以下顺序推进：

1. 使用 `ui.Tester` 运行视图层测试，生成固定尺寸截图并检查关键文本、空状态、错误状态和主题。
2. 使用 `Xvfb` + `-tags e2e` 构建 + `mygo-automation` 启动真实 GTK3 窗口，验证窗口类型、导航、元素树、截图和退出清理。
3. 在同一 Xvfb 会话中执行至少 30 分钟 soak，保存 `soak.csv` 和结束前截图。
4. 如果评审者需要人工观察，仅在评审期间启动 x11vnc 或 noVNC，绑定 `127.0.0.1`，通过 SSH 隧道访问，结束后立即关闭。
5. 在用户真实桌面完成 GPU、Wayland、输入法、HiDPI、多显示器、托盘和主观流畅度的最终确认。

服务器自动验收通过后，结论应表述为“无显示环境验收通过，真实桌面待确认”，不能表述为“已证明长时间运行不再卡顿”。

### AR-022 新增原生能力验收

- 当验收 Terminal、Raw Config、可视化配置表单或导出能力时，系统应使用对应任务的单元测试、`ui.Tester` 和 Xvfb E2E 证据，不接受仅凭代码存在或手工构建成功判定通过。
- 当验收 Terminal 时，应覆盖 mixed、HTTP、SOCKS、wildcard、IPv4、IPv6 和无监听状态；四类命令必须可见且复制路径不得执行 shell。
- 当验收可视化配置时，应覆盖表单修改写回 JSON、未保存标记、非法输入、未知字段保留、校验失败不应用，以及 `/advanced/raw` 路由截图。
- 当验收导出时，应覆盖成功、取消和写入失败；成功文件权限必须为 `0600`，取消不得创建文件，失败不得遗留不完整产物。
- 当验收依赖真实剪贴板、原生保存对话框、真实内核或真实网络时，自动化不可覆盖的部分必须标记“未验证”并记录人工复现步骤。
- 如果当前工作树包含未提交改动，验收者不得复用旧提交的命令、截图、soak CSV 或“通过”结论；应生成新的 `<run-id>` 并引用当前提交。

## 11. 决策门槛

原型评审时按以下方向决策：

- 继续迁移：核心页面可稳定运行，无显示自动验收通过，真实桌面验收确认资源占用和响应性优于 Wails，且复杂页面具备可行替代路径。
- 局部混合：原生 Shell 和常用页面可行，但复杂配置编辑器仍需 WebView；需单独评审是否接受。
- 暂停 MyGo：关键交互、托盘、GTK3 或长时间稳定性存在阻塞性问题，继续维护 Wails。
- 条件通过：无显示自动验收通过，但真实桌面尚未验收；只能作为继续投入原型的依据，不能作为正式替换 Wails 的最终结论。
